# 怎样完成团队独立代码审查

状态：尚未完成。自动化测试与AI实现自查不能代替实际团队成员阅读代码、提出意见与复核修复。以下是执行方案，不是已发生的审查记录。

## 一次可验收的流程

1. 管理成员冻结待审版本，记录提交号、运行环境和功能范围。在GitHub建立PR，或保留本地差异文件；不要只交截图。
2. 原作者写明改动、测试与已知限制；另一名成员阅读差异并亲自运行关键场景。
3. 审查者记录文件位置、问题、复现步骤、严重程度、建议。没有发现问题也要记录实际审查范围与验证结果，不能为了凑数制造问题。
4. 作者修复并关联问题编号；审查者重新运行原来失败的场景，补充验证证据。
5. 严重问题关闭后，由非作者给出通过意见。保留PR讨论或审查记录、修改前后提交号与测试输出。
6. 管理成员将证据汇总到个人贡献报告；教育成员与编程成员共同签核内容正确性。

## 六人安排建议

| 主责 | 独立检查者 | 本轮重点 |
|---|---|---|
| A：存储与记录 | B | 旧数据库升级、草稿覆盖、事务失败、记录是否保留 |
| B：判题与统计 | C | 沙盒不可用拒绝执行、无限循环、输入输出边界、日期换日、示例排除 |
| C：AI与整合 | A | 不可信学生理由、无效JSON、非原文引用、断网回退、主线程更新 |
| 教育成员：任务与标签 | 编程成员+另一名内容复核者 | 边界答案、歧义、概念关联、误诊用语、题目难度 |
| 设计成员：交互 | 教育/管理成员 | 各章直接进入、无需先答选择题、草稿恢复、小窗口 |
| 管理成员：验收文档 | 至少一名未编写文档成员 | 完成状态与证据一致，不把接口或模拟结果说成真实效果 |

如果某模块有共同作者，换另一位未参与该改动的审查者。教育与设计角色的审查很有价值，但运行隔离等技术模块也必须有能理解实现的独立审查者。

## 逐项检查

- 判题：不同正确实现能通过；打印代替返回会失败；空列表、边界、条件优先级覆盖；测试不能证明全部输入正确。
- 执行边界：学生代码只能通过runner进入；不允许退回无沙盒执行；不能用eval/exec运行模型输出；超时/异常不会卡住界面。
- 隔离限制：macOS专用，本地教学用途；内存轮询不是硬配额，不能作为公网不可信代码服务。检查这项限制是否向使用者说明。
- 数据：不删除旧记录；草稿与正式提交分开；示例通过不算任务完成；环境不可用不拉低代码通过率。
- 统计：选择题与代码分开；分母正确；无记录不是0%正确率；UTC记录按本地日期归组。
- AI：标签合法不代表诊断正确；原文引用存在不代表支持结论；每项仍需教育评估。

## 每个问题的记录模板

- 审查版本 / 日期 / 实际审查者 / 作者：待填写
- 文件与行号 / 问题编号 / 严重程度：待填写
- 观察到的行为 / 期望行为 / 复现步骤：待填写
- 修复提交 / 复核步骤与结果：待填写
- 审查结论与仍存在的限制：待填写
